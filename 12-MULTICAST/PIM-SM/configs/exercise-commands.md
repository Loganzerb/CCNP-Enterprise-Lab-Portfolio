# PIM-SM exercise commands

These commands reconstruct the changes used in the lab. The [verification pages](../verification/README.md) contain the actual captured results. Run one exercise at a time after confirming the static-RP baseline.

## Baseline checks

On R4-LHR:

```cisco
show ip route 10.1.1.0
show ip route 2.2.2.2
show ip pim neighbor
show ip pim rp mapping
show ip igmp groups
show ip rpf 10.1.1.10
show ip rpf 2.2.2.2
show ip mroute 239.1.1.1
```

On MCAST-SOURCE:

```cisco
ping 239.1.1.1 repeat 20
```

While the source is active, compare `show ip mroute 239.1.1.1` on R1–R4. Use `show ip pim tunnel` on R1 to inspect its registration mechanism.

## Case 01 — Change the source RPF path

On R4-LHR, add the temporary route:

```cisco
configure terminal
ip route 10.1.1.0 255.255.255.0 10.24.0.1
end
show ip rpf 10.1.1.10
```

Send traffic from MCAST-SOURCE to `239.1.1.1`. Inspect the group's source entry on R4, R2 and R3. Allow the changed tree to settle before comparing the old branch.

Rollback on R4-LHR:

```cisco
configure terminal
no ip route 10.1.1.0 255.255.255.0 10.24.0.1
end
show ip rpf 10.1.1.10
show ip mroute 239.1.1.1
```

Confirm R4 returns to R3, R3 regains source state and R2's source branch is pruned. [Case and evidence](../troubleshooting/01-rpf-path-change.md)

## Case 02 — Remove the receiver-side RP mapping

On R4-LHR:

```cisco
configure terminal
no ip pim rp-address 2.2.2.2
end
show ip pim rp mapping
```

On MCAST-RECEIVER, join a fresh group:

```cisco
configure terminal
interface GigabitEthernet0/0
 ip igmp join-group 239.2.2.2
end
```

Check `show ip igmp groups` and `show ip mroute 239.2.2.2` on R4, then check the same group on R2.

Restore R4:

```cisco
configure terminal
ip pim rp-address 2.2.2.2
end
show ip mroute 239.2.2.2
```

Confirm R2 now has the receiver branch. The retained exercise ends with this tree check; a new source ping would add traffic verification. [Case and evidence](../troubleshooting/02-receiver-rp-failure.md)

## Case 03 — Remove the source-side RP mapping

First establish a fresh receiver tree. On MCAST-RECEIVER:

```cisco
configure terminal
interface GigabitEthernet0/0
 ip igmp join-group 239.3.3.3
end
```

Verify `show ip mroute 239.3.3.3` on both R4 and R2 before changing R1.

On R1-FHR:

```cisco
configure terminal
no ip pim rp-address 2.2.2.2
end
show ip pim rp mapping
show ip pim tunnel
```

On MCAST-SOURCE:

```cisco
ping 239.3.3.3 repeat 20
```

Retain the full result. For a live repair observation, keep test traffic active from **MCAST-SOURCE**; probes generated by R1 itself use a different source context.

Restore R1-FHR:

```cisco
configure terminal
ip pim rp-address 2.2.2.2
end
show ip pim tunnel
show ip mroute 239.3.3.3
```

Check the intended source `10.1.1.10` on R4 and R2 as well. Save a complete post-repair source ping when repeating the test; the original recovery included a reported reply and captured state. [Case and evidence](../troubleshooting/03-source-rp-failure.md)

## Return to the baseline

Stop temporary probes. Confirm the static RP is restored on all four routers and the temporary source route is absent from R4.

On MCAST-RECEIVER:

```cisco
configure terminal
interface GigabitEthernet0/0
 no ip igmp join-group 239.2.2.2
 no ip igmp join-group 239.3.3.3
end
```

Keep `239.1.1.1`. Verify R4's membership table, source/RP lookups and the baseline group with fresh source traffic. The retained final capture verifies membership cleanup; a new baseline traffic check is a recommended additional check.
