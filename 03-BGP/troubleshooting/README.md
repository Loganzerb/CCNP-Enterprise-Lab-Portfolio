# BGP Troubleshooting Case Studies

This section documents three controlled BGP failures from a multi-AS lab. Each case study follows the same practical workflow: identify the symptom, isolate the control-plane fault using device output, restore the intended configuration, and verify route exchange or reachability. Together, the scenarios demonstrate troubleshooting across BGP adjacency, next-hop resolution, and outbound policy.

| Scenario | Symptom | Root cause | Key diagnostic evidence | Recovery |
|---|---|---|---|---|
| [1 — Wrong remote AS / Bad Peer AS](scenario-1-wrong-remote-as.md) | The B2-ISP-B–O4-EDGE eBGP session remained in `Idle`, and no prefixes were exchanged across that peering. | B2 expected O4 in AS `65001`, while O4 was actually in AS `65000`. | B2 showed `remote AS 65001` and `BGP state = Idle`; O4 logged notification `2/2 (peer in wrong AS)`. Peer-address reachability remained up, isolating the failure to BGP configuration rather than IP connectivity. | Corrected B2's neighbor `remote-as` to `65000`. The session returned to Established, B2 received five prefixes from O4, O4 received six from B2, and O4 restored its BGP route to `203.0.113.0/24` through `10.250.2.2`. |
| [2 — iBGP next-hop reachability](scenario-2-ibgp-next-hop-reachability.md) | O2 retained its iBGP sessions but could not use the path to `172.31.251.0/24` learned through O1. | Removing `next-hop-self` on O1 caused O2 to receive B1's external next hop, `10.250.1.2`, which O2 could not resolve. | O2 marked the O1-learned path's next hop as `10.250.1.2 (inaccessible)`, and `show ip route 10.250.1.2` returned `% Subnet not in table`. The alternate path through O4 remained valid and best. | Restored `next-hop-self` on O1 and performed a soft outbound clear. O2 then saw the O1 path with reachable next hop `10.100.1.1`, selected it as best, and installed `172.31.251.0/24` through that next hop. |
| [3 — Route-map implicit deny](scenario-3-route-map-implicit-deny.md) | The O4–B2 BGP session stayed established, but O4's advertised route set fell to one prefix. | An outbound route-map permitted only `172.31.250.0/24`; without a later catch-all permit, every unmatched prefix was denied implicitly. | O4 advertised `Total number of prefixes 1`, while B2 still showed the AS `65000` neighbor established with one received prefix. B2 retained `172.31.251.0/24` only through the alternate AS `65300 65100` path. | Added an unconditional `permit 20` and performed a soft outbound clear. O4 again advertised five prefixes, and B2 regained the additional `172.31.251.0/24` path from AS `65000` while retaining its alternate best path. |

## Engineering Takeaway

Scenarios 2 and 3 degraded an individual BGP path without causing loss of reachability. In Scenario 2, O2 selected the valid path through O4 when the O1-learned next hop became unreachable. In Scenario 3, B2 retained the affected prefix through the alternate AS `65300` path while O4's outbound policy was repaired. The lab therefore validated not only fault isolation and recovery, but also the operational value of redundant routing paths when a control-plane or policy error removes one route.
